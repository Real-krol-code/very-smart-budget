# Стратегия тестирования приложения Finance App

## 1. Введение и цели тестирования

### 1.1. Продукт
«Finance App» — система управления личным бюджетом: пользователь задаёт категории и распределение дохода , система подтягивает транзакции из имитируемого банка, классифицирует их по правилам, считает «факт vs план», формирует уведомления при 80% и 100% лимита и ведёт цели накопления с рекомендуемым ежемесячным взносом.

### 1.2. Цель тестирования
Подтвердить, что бэкенд корректно и воспроизводимо выполняет финансовые операции пользователя: не теряет, не дублирует и не искажает денежные данные, корректно считает лимиты и пороги, формирует уведомления по согласованным правилам, обеспечивает идемпотентность импорта и изоляцию данных пользователей, а также соответствует критериям приёмки проекта.

## 2. Анализ системы и архитектуры

### 2.1. Архитектура
Монолит на Spring Boot с единым развёртыванием и общей базой PostgreSQL. Слой API отдаёт REST-эндпоинты; доменная логика разделена на модули Transaction, Processor, Goal, Notification; доступ к данным — через JDBC/Spring Data JPA. Аутентификация — JWT. Внешние связи: клиент псевдо-банка (Same-Bank Client) за транзакциями и сервис push-уведомлений (Same Notification Service). Микросервисных контрактов между внутренними модулями нет — это влияет на состав уровней тестирования (см. п. 3).

### 2.2. Компоненты и их назначение

| Компонент | Назначение | Что проверяем |
|---|---|---|
| API Layer | Эндпоинты, маршрутизация, приём запросов | Коды ответов, схемы, валидация, формат ошибок |
| Auth Module | Аутентификация и авторизация, JWT | Срок жизни и валидность токена, изоляция данных |
| Transaction Module | Обработка транзакций за период, приём данных банка | Импорт, дедупликация, сохранение, ручная категория |
| Processor Module | Проценты, категории, периоды, контроль лимитов | Распределение 100%, пересчёт факта, пороги |
| Goal Module | Контроль целей | Создание, прогресс, взнос, дедлайн, статусы |
| Notification Module | Алерты по лимитам и целям, связь с БД, отправка | Формирование события, дедупликация, журнал, доставка |
| PostgreSQL | Хранение данных, ACID | Ограничения, точность денег, ссылочная целостность |
| Планировщик | Периодическая синхронизация (SRC-01) | Расписание, повторный запуск, пропуск, ошибки |
| Same-Bank Client | HTTP-клиент источника транзакций | Обработка ошибок и таймаутов источника |
| Same Notification Service | Канал доставки push (FCM/APNs/Web Push) | Payload, статусы, ошибки провайдера, ретраи |

### 2.3. Взаимодействие компонентов

1. Планировщик инициирует синхронизацию за месяц.
2. Transaction Module запрашивает операции через Same-Bank Client.
3. Полученные операции валидируются и дедуплицируются по идентификатору источника.
4. Новые транзакции сохраняются в PostgreSQL и передаются в Processor Module на классификацию.
5. Processor Module назначает категорию по правилам (мерчант / MCC / ключевые слова) либо оставляет «Без категории».
6. Пересчитываются факт, остаток и доля использования лимита по категориям.
7. Notification Module проверяет пороги 80% и 100%, создаёт событие и запись в центре уведомлений.
8. Push отправляется через Same Notification Service; статус доставки фиксируется.
9. Ручная перекатегоризация обновляет транзакцию, вызывает пересчёт и запись в аудит.

### 2.4. Внешние интеграции и зависимости

| Интеграция | Характер | Зависимость для тестирования |
|---|---|---|
| Псевдо-банк | HTTP/JSON, выгрузка по месяцу | Управляемость ответов: пустой месяц, дубли, ошибки, таймаут |
| FCM / APNs / Web Push | Внешние push-провайдеры | Нужны стабы: успех, 4xx/5xx, недоступность |
| PostgreSQL | СУБД | Изолированная схема на прогон, миграции |
| Планировщик | Внутренний компонент | Управляемый ручной запуск для детерминизма |

### 2.5. Критические точки качества
- Граница импорта: повторный и конкурентный запуск синхронизации, частично совпадающие выгрузки.
- Расчёт распределения: сумма процентов 100%, округление до копеек, остаток.
- Переход через границу периода и часового пояса (в артефактах не определён — Q-05).
- Изменение лимита после уже отправленного алерта.
- Смена категории: пересчёт факта, порогов и исторических событий.
- Отказ push-провайдера между сохранением события и отправкой.

### 2.6. Основные потоки данных
- **Импорт:** банк → нормализация → дедупликация → сохранение → классификация → агрегаты → пороги.
- **Перекатегоризация:** пользователь → валидация категории → сохранение → пересчёт агрегатов → аудит.
- **Алерт:** агрегат категории → проверка порога → событие → журнал уведомлений → push → статус доставки.
- **Цель:** параметры цели → расчёт остатка и срока → рекомендуемый взнос → прогресс при взносах.

## 6. Тестирование API

### 6.1. Исходные данные
API — REST (SRC-01), реализуется Spring Boot (SRC-02). Конкретные пути, схемы и коды фиксируются в OpenAPI-спеке, которая пока что не предоставлена. Поэтому стратегия описывает подход и обязательные проверки, а не перечень эндпоинтов; операции ниже выводятся только из UC-01…UC-12 (бюджет, импорт, транзакции, перекатегоризация, дашборд, уведомления, история, цели).

### 6.2. Направления проверок

| Направление | Что проверяется | Критерий |
|---|---|---|
| HTTP-методы и коды | Соответствие методов семантике операции; коды 200/201/204, 400, 404, 409, 422 (зафиксированы в SRC-04); 401/403 — применимы по предусловию авторизации, но код не согласован (Q-02) | Для каждой операции код и метод стабильны и задокументированы в OpenAPI |
| Структура запроса/ответа | Обязательные и необязательные поля, вложенность, типы, отсутствие лишних полей | Ответ валиден по схеме; необязательные поля не ломают обработку |
| Граничные значения | 0 и отрицательные суммы, лимит 0, проценты 0/100, сумма процентов 99/100/101, суммы с копейками, дедлайн в прошлом и «сегодня», ровно 80,00% и 100,00% | Результат определён требованием или вынесен в Q-список |
| Некорректные входные данные | Невалидный JSON, неверные типы, null, пустые строки, неизвестный ID, слишком длинные строки | Валидационная ошибка, данные не сохранены |
| Бизнес-валидации | Сумма процентов = 100%, недоступная категория, чужой объект, целостность при изменении лимита ниже факта | Валидация выполняется до сохранения, сообщение объясняет причину |
| Обработка ошибок | Единый формат ошибки, отсутствие стектрейсов и внутренних деталей, стабильность кода | Ошибки воспроизводятся, формат одинаков во всех модулях |
| Авторизация и доступ | Запросы без токена, с истёкшим токеном, к данным второго пользователя | Отказ без раскрытия существования чужого объекта |
| Повторные запросы | Повторный импорт за месяц, повторное создание сущности, повторная перекатегоризация | Нет дублей; повтор не меняет уже принятые данные |
| Пагинация, сортировка, фильтрация | Списки транзакций, уведомлений, целей, истории | В артефактах пагинация не описана (Q-06); проверяется после её появления в OpenAPI — границы страниц, стабильность порядка при равных значениях |

### 6.3. Порядок работы
1. Спека OpenAPI — источник истины; набор запросов в Postman соответствует спеке.
2. Позитивные проверки выполняются на эталонном наборе данных, негативные — на изолированном пользователе без побочных эффектов.
3. Каждая API-проверка фиксирует не только код, но и состояние данных (повторное чтение ресурса или SQL-сверка).
4. Регресс — Postman-коллекция (требование SRC-01) плюс автотесты на критические потоки.

## 7. Тестовые данные и тестовое окружение

### 7.1. Окружения

| Контур | Назначение | Состав |
|---|---|---|
| Local | Разработка и отладка проверок | Приложение + локальная PostgreSQL + мок псевдо-банка |
| CI | Автоматический регресс на каждый PR | Изолированная PostgreSQL на прогон, стабы банка и push-провайдеров |
| Demo / приёмочный | Прогон кейсов и демонстрация | Приложение + мок псевдо-банка + стаб push-провайдера (Q-07) |

Отдельного DevOps-контура в проекте нет (команда до 5 человек) — окружения поднимаются разработчиками при участии тестировщика.

### 7.2. Требования к тестовой БД
- PostgreSQL (SRC-02), схема разворачивается миграциями, а не вручную.
- Отдельная схема или база на каждый прогон; между прогонами — полный сброс.
- Фиксированная точность денежных полей (2 знака) — проверяется отдельно.
- Обязательные ограничения уникальности для дедупликации транзакций и внешние ключи между транзакцией, категорией и бюджетом.

### 7.3. Моки и заглушки
- Псевдо-банк — мок-API из комплекта проекта (SRC-01); для негативных сценариев — управляемый стаб с настраиваемыми ответами (пустой месяц, дубли в выдаче, 4xx/5xx, таймаут).
- Push-провайдеры (FCM/APNs/Web Push) заменяются стабом с проверкой payload и фиксацией статуса доставки.
- Планировщик в тестах запускается управляемо (ручной триггер), иначе проверки недетерминированы.

### 7.4. Учётные записи и изоляция
- Не менее двух пользователей (A и B) — для проверок доступа к чужим данным во всех модулях.
- Пользователь без бюджета и транзакций (пустые состояния).
- Пользователь с полным бюджетом и эталонным набором транзакций.
- Данные разных пользователей не пересекаются; каждый прогон работает на своей паре пользователей.

### 7.5. Подготовка данных

| Набор | Состав | Назначение |
|---|---|---|
| Эталонный набор транзакций | 240 операций за месяц (≥200 по AC), из них 172 классифицируются автоматически (71,7%) — значения из CLS-11 | Метрика ≥200 операций и ≥70% авто, базовая линия регресса |
| Набор дублей | Повторная выгрузка того же месяца; частичное пересечение; операция без идентификатора; изменённая операция | Идемпотентность импорта |
| Набор порогов | Категории, дающие 79,99%, 80,00%, 80,01%, 100,00%, 105% | Границы алертов |
| Набор бюджета | Три равные категории на 100 000; суммы процентов 99/100/101; дубль категории; категория без лимита; удалённая категория | Распределение и пересчёт |
| Набор правил | Точный мерчант, вхождение с «ё»/«е» и разным регистром, MCC точный/список/диапазон, ключевое слово, конфликтующие правила | Автоклассификация |
| Набор целей | Остаток 100 000 и 3 месяца; дедлайн в прошлом; менее месяца до дедлайна; накоплено больше цели; несколько целей | Расчёт взноса и прогресса |

### 7.6. Очистка и воспроизводимость
- Подготовка и очистка — скриптами (SQL-фикстуры), а не ручными действиями в БД.
- Каждый прогон начинается с чистого состояния и эталонного набора; результат не зависит от предыдущих прогонов.
- Даты и «текущий месяц» фиксируются на уровне окружения, иначе результаты по периодам, порогам и целям не воспроизводятся.
- Повторный запуск любого кейса не должен требовать ручной правки данных.

## 9. Приоритизация тестирования

| Приоритет | Проверки | Обоснование |
|---|---|---|
| P0 (блокируют выпуск) | Импорт за месяц и идемпотентность; распределение бюджета и сумма процентов 100%; пересчёт факта при перекатегоризации и изменении лимита; корректность сохранения денежных значений; алерты 80%/100% (порог и однократность); изоляция данных пользователя и валидность JWT | Ошибка в любом из пунктов приводит к искажению финансовых данных или к ложным/пропущенным уведомлениям — это ядро продукта и то, что демонстрируется |
| P1 (высокая) | Автоматическая классификация по всем типам правил и разрешение конфликтов; ручная перекатегоризация с записью аудита; центр уведомлений (список, состав, доступ); цели (создание, взнос, прогресс, дедлайн); контракт OpenAPI и работоспособность Postman-коллекции | Влияют на ключевые пользовательские сценарии и на приёмку продукта по SRC-01 |
| P2 (средняя) | Планировщик и повторные запуски; аудит и история (полнота, старые/новые значения); копирование бюджета на следующий период; топ расходов; возвраты и отмены; устойчивость к недоступности псевдо-банка и push-провайдера | Важны для целостности, но отказ не обнуляет основной сценарий демонстрации |
| P3 (низкая) | Тексты и формулировки сообщений об ошибках и уведомлений; редкие комбинации параметров; косметические аспекты формата ответов | Не влияют на расчёт и сохранность данных |

## 10. Критерии начала и завершения тестирования

### 10.1. Критерии входа

| Условие | Проверка |
|---|---|

| Эталонный набор данных и фикстуры загружаются скриптом | Повторная загрузка на чистой базе |
| Определены тестовые учётные записи и пользователи для проверок доступа | Загрузка двух пользователей |
| Планировщик запускается управляемо | Ручной триггер синхронизации |
| Готовы тест-кейсы P0 | Ревью набора |

### 10.2. Критерии выхода

| Критерий | Значение |
|---|---|
| Покрытие P0 | 100% выполнено |
| Покрытие P1 | Не менее 95% выполнено |
| Открытые блокирующие и критические дефекты | 0 |
| Дефекты высокой важности (P1) | Закрыты либо имеют согласованный workaround и зафиксированы в известных проблемах |

| Объём импорта | Не менее 200 транзакций за месяц подтверждён прогоном |
| Соответствие OpenAPI | Ответы соответствуют схеме, расхождений нет |
| Воспроизводимость демо-данных | Данные разворачиваются с нуля без ручных шагов |
| Регресс | Полный набор пройден, падений нет |

# 11. Риски и ограничения тестирования

| Риск | Вероятность | Влияние | Способ минимизации |
|---|---|---|---|
| Требования неполны или противоречивы (сумма ≠ 100%, поведение при изменении операции в источнике, правило расчёта при отсутствии полных месяцев) | Высокая | Высокое | Список вопросов Q-01…Q-12; фиксация допущений до старта модуля; тест-кейсы параметризуются под финальное решение |
| Изменение API-контракта без уведомления QA | Средняя | Высокое | Контрактные проверки по OpenAPI в CI; ревью изменений спеки; тег версии в коллекции Postman |
| Нестабильность мока псевдо-банка | Средняя | Среднее | Управляемый стаб для негативных сценариев; фиксированные ответы; прогон на детерминированных данных |
| Ошибки синхронизации: потеря или частичное применение пачки операций | Средняя | Высокое | Проверки транзакционности и повторного запуска; сверка API ↔ БД после импорта |
| Дублирование операций при повторном и параллельном импорте | Высокая | Критическое | Автотесты идемпотентности, включая параллельный запуск; проверка уникального ограничения в БД |
| Ошибки классификации (неверная категория, нестабильный результат) | Высокая | Высокое | Таблица решений по приоритетам правил; проверка повторяемости; метрика ≥70% с фиксированным набором |
| Некорректные финансовые расчёты (округление, остаток, доля лимита) | Средняя | Критическое | Unit-проверки формул, эталонные значения в кейсах, SQL-инварианты |
| Потеря обновлений при параллельном изменении лимита и перекатегоризации | Средняя | Высокое | Проверки конкурентного доступа; критерий отсутствия потерянных обновлений |
| Недоступность push-провайдеров | Высокая | Среднее | Стабы с 4xx/5xx и таймаутом; проверка сохранения события в центре уведомлений и статуса доставки |
| Недостаточность или нестабильность тестовых данных | Средняя | Высокое | Эталонный набор в репозитории, скрипты подготовки и очистки, изоляция пользователей |
| Отсутствие OpenAPI-спеки и Postman-коллекции на старте | Высокая | Высокое | Блокирующее условие входа для API-регресса; до появления спеки проверки выполняются по UC и фиксируются вручную |
