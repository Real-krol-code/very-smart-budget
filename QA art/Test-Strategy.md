# Стратегия тестирования приложения Finance App

# 1. Общие сведения

Документ описывает стратегию тестирования бэкенда сервиса Finance App: что проверяем, какими методами, на каких данных и окружениях, по каким критериям считаем качество достаточным для демонстрации и защиты проекта.

Стратегия фиксирует границы ответственности QA, подход к тест-дизайну, реестр рисков, уровни и виды тестирования, требования к тестовым данным, план проверок по модулям, критерии входа и выхода, порядок работы с дефектами и отчётностью.

|---|---|---|

## 1.4 Границы тестирования

Объект тестирования — только бэкенд: REST API, доменная логика, PostgreSQL, планировщик, фоновые обработчики, интеграции с псевдо-банком и push-провайдерами, OpenAPI-спецификация и демо-данные. Фронтенд и мобильные приложения рассматриваются исключительно как потребители API: их реализация, вёрстка, навигация, стилистика и поведение на устройстве не тестируются.

| Область | Статус | Комментарий |
|---|---|---|
| REST API и бизнес-логика бюджета, лимитов, транзакций, целей | В области | Основной объём функционального тестирования |
| Импорт из псевдо-банка, идемпотентность, повторные и конкурентные вызовы | В области | Критический риск дублирования денежных данных |
| Движок правил классификации и ручная перекатегоризация | В области | Включая приоритеты правил и сохранение ручного выбора |
| Пересчёт факта и дашборд «факт vs план» на уровне API | В области | Проверяются агрегаты и их согласованность, не отрисовка |
| Пороговые алерты 80% и 100%, дедупликация, центр уведомлений | В области | Включая порядок и повторяемость событий |
| Отправка push через FCM, APNs, Web Push | В области | Проверяется запрос к провайдеру, payload, ретраи, обработка ошибок |
| Цели: прогресс, рекомендуемый взнос, дедлайны | В области | Включая граничные и календарные случаи |
| Аудит действий и история изменений категорий | В области | Полнота, неизменяемость, изоляция данных |
| Планировщик синхронизации | В области | Расписание, блокировки, пропущенные запуски, ретраи |
| OpenAPI, Postman-коллекция, демо-данные | В области | Валидность, соответствие реализации, воспроизводимость |
| PostgreSQL: схема, ограничения, миграции, индексы | В области | Проверки целостности и производительности запросов |
| UI, вёрстка, стилистика Т-Банка, анимации | В области | Рассматривается после готовности серверной составляющей |
| Реальные банковские интеграции и платёжные операции | Вне области | В проекте имитируются псевдо-банком |

# 2. Контекст и архитектура

## Компоненты бэкенда

| Компонент | Ответственность | Что проверяем |
|---|---|---|
| API-слой | Валидация запросов, аутентификация, маршрутизация, формат ошибок | Коды ответов, схемы, граничные значения, problem+json, идемпотентные заголовки |
| Аутентификация и пользователи | Регистрация, вход, JWT, обновление токена, роли | Срок жизни токена, подпись, изоляция пользователей, отзыв доступа |
| Бюджет и категории | Категории, лимиты, проценты, распределение дохода, период | Валидация сумм и долей, округление, изменение лимита в середине периода |
| Транзакции | Хранение, фильтрация, ручная категория, заметки | Пагинация, фильтры, неизменяемость полей, перекатегоризация |
| Классификация | Движок правил, приоритеты, применение к импорту | Конфликты правил, покрытие, стабильность при повторном импорте |
| Агрегация и дашборд | Факт, план, процент, остаток, топ расходов | Согласованность сумм, кэш, пересчёт после изменений |
| Алерты | Расчёт порогов, дедупликация, создание событий | Границы 80/100, однократность, сброс в новом периоде |
| Уведомления | Очередь, воркер, интеграции FCM/APNs/Web Push, центр | Доставка, ретраи, недействительные токены, статусы, история |
| Цели | Создание, прогресс, взносы, рекомендуемый платёж | Формула, округление, месяцы до дедлайна, завершение |
| Аудит | Журнал изменений и событий | Полнота, актор, до/после, неизменяемость, доступ |
| Интеграционный клиент | HTTP-вызовы псевдо-банка и push-провайдеров | Таймауты, ретраи, разбор ошибок, идемпотентные ключи |
| PostgreSQL | Хранение данных, ограничения, индексы, миграции | Уникальность, внешние ключи, точность денег, планы запросов |

## Внешние интеграции и тестовые двойники

| Интеграция | Протокол | Тестовый двойник | Ключевые проверки |
|---|---|---|---|
| Псевдо-банк, выгрузка транзакций за месяц | HTTP/JSON, постранично | Мок-API из комплекта проекта плюс WireMock-стаб для негативных сценариев | Пагинация, пустой месяц, ошибки 4xx/5xx, таймаут, дубликаты в выдаче |
| Web Push | HTTPS, VAPID | WireMock | Заголовки VAPID, TTL, payload, 404/410, недействительная подписка |

# 3. Цели и критерии приёмки

## Цели тестирования

- Подтвердить реализацию всех сценариев и критериев приёмки на уровне бэкенда, а не на уровне интерфейса.
- Найти дефекты в денежных расчётах, идемпотентности, изоляции данных и доставке уведомлений — там, где цена ошибки максимальна.
- Доказать воспроизводимость демонстрации: чистый стенд, демо-данные, Postman-коллекция и предсказуемый результат за один прогон.
- Обеспечить автоматизированный регресс, который можно запускать на каждом изменении без ручной подготовки.
- Сформировать проверяемые свидетельства для принимающей стороны: отчёты, SQL-выборки, артефакты прогонов.
