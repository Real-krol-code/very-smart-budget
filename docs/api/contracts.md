# Контракты приложения личного бюджета

Версия 1.0. MVP покрывает UC-01–UC-16. Клиент работает с API монолита Spring Boot. Внутри монолита модули взаимодействуют через Java-интерфейсы и используют PostgreSQL. HTTP-вызовы к Same-Bank и Same Notification Service выполняют соответствующие модули.

## Предметная модель

| Сущность | Идентификатор и связи | Модуль-владелец | Представление в контрактах |
|---|---|---|---|
| Пользователь | Внутренний `userId`. Владеет бюджетами, транзакциями, целями, уведомлениями и историей. | Auth | `sub` в JWT и `Actor` во внутренних вызовах. `externalUserId` и `recipientId` определяются по отдельным привязкам. |
| Бюджет | `budgetId`. Один на пользователя и календарный месяц. Содержит плановый доход и распределение. | Processor | `Budget`, `BudgetCreate`, `BudgetUpdate`. |
| Распределение по категории | Пара «бюджет + категория». Хранит долю, по которой рассчитывается денежный лимит. | Processor | `allocations[]` в бюджете. |
| Категория расходов | `categoryId`. Используется в распределении бюджета, правилах классификации и назначении категории транзакции. | Processor | `Category`, ссылки по `categoryId`, снимки в истории и уведомлениях. |
| Правило классификации | ID правила. Связывает признак операции и его приоритет с категорией расходов. | Processor | Внутренний вызов `classify` принимает признаки операции и возвращает результат с ID категории при совпадении. |
| Транзакция | `transactionId`. Принадлежит пользователю, имеет ноль или одну категорию. Внешняя операция идентифицируется ключом «источник + внешний пользователь + внешний ID операции». | Transaction | `BankOperation` на входе импорта, `Transaction` в Client API. |
| Изменение категории | `eventId`. Связано с пользователем и транзакцией, содержит инициатора, время и снимки категорий. | Transaction | `HistorySummary` и `HistoryEvent`. |
| Цель накопления | `goalId`. Принадлежит пользователю, задаёт целевую сумму и дедлайн. | Goal | `GoalCreate` и `Goal`. |
| Пополнение цели | `contributionId`. Принадлежит одной цели, хранит сумму и время. | Goal | Команда `addGoalContribution` и `ContributionResult`. |
| Уведомление о лимите | `notificationId`. Связано с пользователем, категорией, месяцем и порогом. Хранит значения расходов и лимита на момент события. | Notification | `NotificationSummary` и `Notification` в Client API, `PushRequest` на границе доставки. |

Дашборд, использование лимита и прогресс цели — расчётные представления. Запуск импорта и заявка на push — технические записи обработки. Внешний `externalTransactionId` используется для сверки импорта, а клиент обращается к операции по внутреннему `transactionId`. В истории названия категорий берутся из сохранённых снимков.

## Границы обмена

| Граница | Спецификация | Ответственность |
|---|---|---|
| Клиент → API Layer | [Client API](client-api.openapi.yaml) | Вход, чтение и изменение данных пользователя |

## Интерфейсы модулей

Сигнатуры задают порты приложения. Идентификаторы имеют тип `String`, деньги хранятся в `long` в копейках, месяц представлен `YearMonth`, дата дедлайна — `LocalDate`, моменты событий — `Instant`. Списковые методы возвращают пустую коллекцию для пустой выборки. Для страниц `Page<T>` содержит `items` и nullable `nextCursor`. DTO совпадают с одноимёнными моделями Client API, где ниже не указано иное.

```java
interface AuthModule {
    Session login(Credentials credentials);
    Actor authenticate(String bearerToken);
}

interface TransactionModule {
    ImportResult synchronize(ImportRequest request);
    Page<Transaction> list(String userId, YearMonth month, PageQuery query);
    Transaction get(String userId, String transactionId);
    CategoryChange changeCategory(Actor actor, String transactionId, String categoryId, long version);
    Page<HistorySummary> history(String userId, Optional<String> transactionId, PageQuery query);
    HistoryEvent historyEvent(String userId, String eventId);
}

interface ProcessorModule {
    List<Category> categories(String userId);
    Budget createBudget(String userId, BudgetCreate request, String idempotencyKey);
    Budget getBudget(String userId, String budgetId);
    Budget updateBudget(String userId, String budgetId, BudgetUpdate request);
    Dashboard dashboard(String userId, YearMonth month);
    Classification classify(String userId, ClassificationInput input);
    List<CategoryUsage> recalculate(String userId, YearMonth month, Set<String> categoryIds);
}

interface NotificationModule {
    void evaluate(LimitUsageChange change);
    Page<NotificationSummary> list(String userId, PageQuery query);
    Notification get(String userId, String notificationId);
}

interface GoalModule {
    List<Goal> list(String userId);
    Goal get(String userId, String goalId);
    Goal create(String userId, GoalCreate request, String idempotencyKey);
    ContributionResult contribute(String userId, String goalId, long amountMinor, String idempotencyKey);
}
```

| Тип | Поля и результат |
|---|---|
| `Credentials`, `Session`, `Actor` | Логин и пароль → токен, тип Bearer, срок в секундах. Проверка токена → идентификатор пользователя из JWT `sub`. |
| `PageQuery` | Размер страницы и nullable курсор. Курсор связывает пользователя, маршрут и фильтры. Сортировка по времени события и ID по убыванию. |
| `ImportRequest` | Внутренний и внешний идентификаторы пользователя, код источника, месяц. Связь пользователей хранится в конфигурации подключения. |
| `ImportResult` | ID запуска, статус `COMPLETE / PARTIAL / FAILED`, счётчики `received / added / skipped / rejected / unprocessed / changedDuplicates / classificationFailed`, причины ошибок. `changedDuplicates` входит в `skipped`, `classificationFailed` входит в `added`. |
| `ClassificationInput`, `Classification` | ID, направление, описание, nullable мерчант и MCC → `MATCHED` с ID категории, `NO_MATCH` или `CATEGORY_UNAVAILABLE`. |
| `CategoryChange` | Обновлённая операция и использование лимитов затронутых категорий. |
| `LimitUsageChange` | Пользователь, месяц, снимок категории, расходы и лимит до и после изменения. Отсутствующий лимит представлен пустым значением. |
| `ContributionResult` | ID пополнения, сумма, время и состояние цели после операции. |

API Layer переводит ошибки авторизации в `401`, несоответствие запроса схеме в `400`, недоступный объект в `404`, конфликт версии или ключа в `409`, нарушение бизнес-правила при корректной схеме в `422`. Истёкший курсор возвращает `410`. Для ключевых нарушений правила передаются в `details[].reason`, например `SHARES_TOTAL_NOT_100_PERCENT`, `BUDGET_MONTH_LOCKED`, `CATEGORY_UNAVAILABLE`, `GOAL_NOT_ACTIVE`, `AMOUNT_EXCEEDS_REMAINING`, `DEADLINE_IN_PAST`. Коды `500/503` позволяют клиенту показать ошибку загрузки или сохранения. После неопределённого исхода команды клиент использует правила повтора из Client API.

## Данные, порядок обработки и повтор

**Импорт.** Планировщик вызывает `synchronize` для пользователя и месяца. Transaction Module читает все страницы Same-Bank и проверяет обязательные поля, валюту RUB, положительную сумму, принадлежность месяцу и формат MCC. Запись с ошибкой увеличивает `rejected`. Уникальный индекс `(source, external_user_id, external_transaction_id)` защищает от параллельных вставок. При конфликте ключа модуль сравнивает банковские поля, увеличивает `skipped` и дополнительно `changedDuplicates`, если поля отличаются. Успешно сохранённые записи учитываются в `added`. При ошибке записи оставшиеся полученные операции учитываются в `unprocessed`, обход прекращается, результат фиксируется по фактически завершённым операциям. Сбой даёт `PARTIAL`, если обработана часть полученных данных, иначе `FAILED`. Пустой ответ даёт `COMPLETE` с нулевыми счётчиками. При истечении курсора повторный запуск начинает обход заново.

**Классификация.** Новая операция сначала сохраняется с пустой категорией. Затем Transaction Module запрашивает `classify` у Processor Module. Активные правила применяются в порядке «мерчант → MCC → ключевые слова», внутри уровня — по заданному приоритету, при равенстве — по ID правила. Мерчант сравнивается целиком, ключевое слово ищется в описании, регистр и внешние пробелы игнорируются. Если категория правила недоступна или запись результата не удалась, операция сохраняет пустую категорию. Назначение категории использует условное обновление по версии операции, чтобы автоматическое правило не перезаписало ручной выбор. При успешном назначении пересчитывается использование лимита. Неклассифицированные расходы видны в дашборде с момента импорта.

**Бюджет.** Один бюджет на пользователя и календарный месяц. Доход положительный. Доли уникальных доступных категорий в базисных пунктах суммируются до 10 000. Лимиты округляются вниз до копейки, остаток распределяется по убыванию дробной части, при равенстве — по ID категории. Учитываются расходные операции `DEBIT`. Дашборд включает общие расходы, отдельную сумму без категории и топ из десяти расходных операций по сумме, затем по времени и ID по убыванию. При отсутствии бюджета `budget = null`, при отсутствии операций суммы равны нулю. Показатели категории без лимита возвращаются с нулевым лимитом и `usedBasisPoints = null`. Остаток лимита равен лимиту минус расходы, отображаемая доля округляется вниз. Обновление допускается только для текущего месяца. Существующие операции сохраняют свои категории при изменении распределения бюджета.

**Категория и история.** Transaction Module проверяет владельца, версию и допустимость категории. Совпадение с текущей категорией при актуальной версии возвращает текущее состояние без новой записи. Изменение, снимки старой и новой категории и постановка уведомлений сохраняются в одной транзакции. Processor Module пересчитывает прежнюю и новую категории за месяц операции. При удалении или недоступности связанного объекта сохранённая история и уведомления остаются доступны владельцу, `objectUrl` возвращается как `null`.

**Лимиты и push.** Processor Module передаёт в `evaluate` изменения после автоматической или ручной категоризации и пересчёта бюджета. Порог проверяется по точному отношению без округления. Порог считается пересечённым, если прежнее значение было ниже, а новое равно порогу или выше. При появлении положительного лимита прежнее использование для проверки считается нулевым. При нулевом или отсутствующем новом лимите проверка заканчивается. Если пересечены оба порога, оценивается только 100%. Один и тот же порог подавляется уникальным ключом `(userId, categoryId, month, threshold)`, в том числе после снижения расходов и повторного пересечения. Событие и запись очереди отправки создаются атомарно, изменения для одной категории и месяца обрабатываются последовательно. Рабочий процесс очереди получает внешний ID получателя из привязки пользователя, отправляет запрос и фиксирует `ACCEPTED` с ID заявки или ошибку. При сетевых ошибках, `429` и `5xx` используются тот же ID и до двух повторов с задержками 1 и 4 секунды, либо дольше согласно `Retry-After`, в пределах 24 часов. При отсутствии привязки фиксируется отказ отправки, уведомление по-прежнему доступно в центре.

**Цели.** При создании накоплено 0, дедлайн может быть сегодня или позже. Остаток равен целевой сумме минус накопленная. Прогресс в базисных пунктах округляется вниз. Оставшиеся месяцы — минимальное целое число `n ≥ 0`, для которого `today.plusMonths(n)` достигает дедлайна; после дедлайна число месяцев равно нулю. Для активной цели взнос округляется вверх до копейки и рассчитывается по `max(1, n)`. Достигнутая цель получает статус `ACHIEVED` и взнос 0. Просроченная недостигнутая цель получает `OVERDUE` и взнос `null`. Пополнять можно только активную цель, включая день дедлайна. Вставка пополнения и изменение суммы выполняются атомарно с блокировкой цели перед проверкой остатка.

**Идемпотентность клиентских команд.** Для создания бюджета, создания цели и пополнения ключ относится к пользователю, операции и целевому ресурсу. Первое успешное выполнение атомарно сохраняет результат на 24 часа, повтор с тем же телом возвращает этот результат. Тот же ключ с другим телом даёт `409`. После истечения срока клиенту следует сверить состояние перед повторением команды. Для оптимистической блокировки текущая версия проверяется при записи, включая случай одновременного обновления.

## Матрица покрытия

| UC | Операция или вызов | Альтернативные исходы и проверка |
|---|---|---|
| 01 | `createBudget` | Поля и формат — 400, недопустимые значения и доли — 422, повтор месяца — 409, сбой сохранения — 500/503. |
| 02 | `synchronize → listBankTransactions` | Пустая выборка, недоступность источника, частично некорректный пакет, все операции уже есть, сбой сохранения. Проверить счётчики и состояние записей. |
| 03 | Уникальный ключ импорта | Некорректный ID отклоняется, повтор и параллельный запуск сохраняют одну запись, изменившийся дубль отражается в счётчиках. |
| 04 | `classify → recalculate → evaluate` | Нет правила, несколько правил, недоступная категория, сбой записи результата. |
| 05 | `changeTransactionCategory` | Текущая категория — 200 без эффекта, недоступная категория — 422, чужая операция — 404, конфликт — 409, сбой — 500/503. |
| 06 | `getDashboard` | Нет бюджета, нет операций, неклассифицированные расходы, ошибка загрузки — 500/503. |
| 07 | `evaluate → submitPush`, 80% | Ниже порога, ровно 80%, повторное пересечение, скачок сразу за 100%, отказ push. |
| 08 | `evaluate → submitPush`, 100% | Ниже порога, ровно 100%, повтор, скачок через оба порога, смена лимита, отказ push. |
| 09 | `createGoal` | Отсутствуют поля или сумма не соответствует схеме — 400, дедлайн в прошлом — 422, сбой сохранения — 500/503. |
| 10 | `getGoal` | Достигнута, меньше месяца, последний день, просрочена, объект недоступен — 404, ошибка загрузки — 500/503. |
| 11 | `listNotifications`, `getNotification` | Пустая страница, `objectUrl = null`, ошибка загрузки — 500/503. |
| 12 | `listHistory`, `listTransactionHistory`, `getHistoryEvent` | Пустая страница, снимки при недоступном объекте, ошибка загрузки — 500/503. |
| 13 | `listTransactions`, `getTransaction` | Пустая страница, категория `null`, недоступная операция — 404, ошибка загрузки — 500/503. |
| 14 | `login` | Пропущены поля — 400, неверные данные — 401, сервис входа недоступен — 503. |
| 15 | `updateBudget` | Некорректные данные и закрытый месяц — 422, конфликт версии — 409, сбой сохранения — 500/503. |
| 16 | `addGoalContribution` | Сумма вне формата — 400, превышение остатка и неактивная цель — 422, повтор ключа, конкурентные пополнения, сбой сохранения — 500/503. |

Границы месяца, «сегодня» и дедлайн используют единый настраиваемый часовой пояс. Исправление ошибочного пополнения, автоматический учёт накоплений и обновление ранее импортированных банковских операций требуют отдельных решений.
